Q4 data migration plan

Move billing_events off the shared Postgres cluster onto its own partitioned cluster before the December 8 change freeze, with no gap in invoicing and a rollback path at every step.

Why now

The table is 1.9 TB and grows about 140 GB a month. It accounts for 61% of write IOPS on pg-shared-02, and nightly invoice runs now push p99 latency for unrelated services past 800 ms. Splitting it out also unblocks the retention policy Finance asked for in Q3.

  • Partition by month on created_at; detach partitions older than 25 months to cold storage.
  • Keep the existing primary key so downstream consumers need no changes.
  • Run the backfill from a replica, never the primary.

Dual-write toggle

Writes go through the existing BillingEventsRepo. The flag is read per request so we can turn it off without a deploy.

# config/flags/billing.yaml
billing_events_dual_write:
  enabled: true
  target: pg-billing-01
  shadow_reads: 0.05      # compare 5% of reads, log mismatches
  fail_open: true         # a failed shadow write never blocks the primary

If the reconciler reports any divergence during dual-write, we restart the 7-day clock. No exceptions for “small” mismatches; those are exactly the ones that end up on an invoice.

Priya Raman, review comment on v5

Before cutover

  • Provision pg-billing-01 with 4 TB gp3 and PITR enabled
  • Land migration 0042_partition_billing_events.sql
  • Load-test invoice run against the new cluster at 2× October volume
  • Write the rollback runbook and rehearse it once in staging
  • Get Finance sign-off on the December 1 cutover window

Rollback

Until the old table is dropped (no earlier than January 15), rollback is a flag flip: set target back to pg-shared-02 and replay the write-ahead queue from the cutover timestamp. Expected recovery time is under 20 minutes.
